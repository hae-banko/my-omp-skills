# Experience First

Apply when product, UX, or feature-scope tradeoffs come up. Choose user delight over implementation convenience; ship fewer polished features over more rough ones.

When implementation convenience conflicts with user experience, choose the user's experience. Foundations serve the experience; foundations govern sequence, while experience governs the target.

**Why:** Code is written once but experienced constantly. Saving developer effort by shifting ambiguity, friction, or rough edges onto the consumer degrades product value and increases downstream support load.

- **Justify every surface:** Every feature, UI control, configuration flag, and optional parameter must justify its existence.
- **Ship less, ship better:** A deeply polished experience with three focused capabilities beats an unpolished collection of ten half-implemented features.
- **Prototype before committing:** Validate ergonomics in throwaway prototypes before cementing architecture or production code.
- **Get the details right:** Focus on responsive feedback, precise alignment, consistent spacing, clear transitions, and helpful error messaging.
- **Tighten the core workflow:** Every component and option must serve the central path or get out of the way.
- **Identify the consumer:** The user is whoever consumes the work: an end-user for UI, a calling engineer for an API, or the next maintainer reading the code. Explain trade-offs and impact from their perspective.
